# 小狼杀：阶段6测试与验收设计

## 文档状态

- 当前阶段：阶段6测试与验收设计
- 上游输入：阶段1需求定义、阶段2业务逻辑与 UX/User Flow、阶段3数据结构与核心模型、阶段4技术选型、阶段5系统与接口设计、阶段5.5极简聊天室式 MVP 前端设计
- 当前目标：定义后续 AI Agent 可执行、可审查、可量化的测试与验收标准
- 编码状态：本阶段不输出业务代码、不输出测试代码

## 锁定决策

1. 阶段6采用“完整一局流程验收 + 模块验收矩阵”的组合方式。
2. 技术正确性由 AI 自动化测试、Developer Agent 自测和 Reviewer Agent 审查负责。
3. 项目负责人不逐条验收技术测试，只亲自跑通一次 MVP，并判断基础体验是否达标。
4. 验收用例采用编号化格式，便于后续阶段拆分开发任务与审查任务。
5. 所有局中 UI、AI 局中任务和规则动作不得绕过 `VisibleInformationSnapshot`、`GameAction`、规则引擎与 `TruthEvent` 边界。
6. 阶段6不得推翻阶段1至阶段5.5锁定规则；若发现冲突，必须先回溯修正上一阶段文档。

## 回溯清单

本阶段设计未发现必须回溯阶段5或阶段5.5的冲突点。

阶段5.5已明确：聊天室消息流是 UI 派生视图，不是事实源；结构化按钮提交 `GameAction`；局中消息只能来自过滤后的可见信息、`PendingAction`、Store 状态和 `AppError`。阶段6在此基础上补充验收标准，不改变接口设计。

## 验收责任分工

| 责任方 | 负责内容 | 不负责内容 |
| --- | --- | --- |
| Developer Agent | 根据阶段文档实现功能，并按本阶段编号用例补充自动化测试或可重复验证脚本 | 自行修改锁定规则、跳过信息隔离、以“体验需要”为由绕过规则引擎 |
| Reviewer Agent | 对照 `Agent.md`、阶段文档和本阶段用例审查实现、测试结果与边界遵守情况 | 直接替 Developer 修改代码 |
| 项目负责人 | 跑通一次 MVP，判断是否符合“一个人能玩下去的 AI 狼人杀”基础体验 | 逐条检查规则引擎、接口、存储、AI Proxy 或信息隔离测试 |

阶段9进入双 Agent 开发时，Reviewer Agent 必须引用本阶段编号用例出具通过结论或驳回单。

## 编号规则

| 前缀 | 范围 |
| --- | --- |
| `E2E` | 一局完整流程验收 |
| `RULE` | 规则引擎与胜负结算验收 |
| `STATE` | 状态机与异常路径验收 |
| `UI` | 聊天室式 MVP 页面验收 |
| `AI` | AI Client / AI Proxy / 降级验收 |
| `STORE` | IndexedDB、快照、事件重放与刷新恢复验收 |
| `ISO` | 信息隔离红线验收 |
| `REVIEW` | 终局复盘与追问验收 |
| `HITL` | 项目负责人体验验收 |

每条用例后续实现时应至少包含：前置条件、操作步骤、期望结果、失败判定、建议测试类型。建议测试类型只用于指导 AI 选择验证方式，不要求项目负责人执行。

建议测试类型：

- `unit`：适合纯函数、规则引擎、可见信息过滤。
- `integration`：适合 Store、Storage、AI Client/Proxy、跨模块状态推进。
- `e2e`：适合页面、完整一局、刷新恢复、人工可观察体验。
- `manual`：只用于项目负责人最终跑通 MVP。

## 一局完整流程验收

### E2E-001：标准局从开局进入复盘

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 无进行中对局，进入 `mode_select` |
| 操作步骤 | 点击 `开始标准局`；确认身份；完成首夜行动或等待；进入天亮播报；完成发言、投票、可能的平票、放逐、遗言和后续夜晚；直到触发胜负进入 `review` |
| 期望结果 | 一局 5 人 MVP 可以从开始走到终局复盘；每次状态推进都有明确消息、可用操作或等待提示 |
| 失败判定 | 任一阶段无可用下一步、页面卡死、跳过必要规则结算、无法进入复盘 |
| 建议测试类型 | `e2e` |

### E2E-002：自由局手动选身份后可跑通

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 无进行中对局，进入 `mode_select` |
| 操作步骤 | 点击 `练习/自由局`；进入 `role_setup`；选择狼人、预言家或村民之一；确认身份；继续完整一局 |
| 期望结果 | 手动身份只影响真人身份选择，不破坏 5 人最简局其他座位补位、流程推进和胜负结算 |
| 失败判定 | 未选身份也能开始、非法身份被接受、AI 补位缺失、流程无法进入 `role_reveal` |
| 建议测试类型 | `e2e` |

### E2E-003：真人死亡后旁观到复盘

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 真人玩家在局中死亡，`humanParticipationState = dead_spectating` |
| 操作步骤 | 选择 `继续旁观`；观察后续 AI 自动推进；直到胜负产生进入 `review` |
| 期望结果 | 真人死亡后不能继续发言、投票或夜晚行动；只能看到公开消息和旁观状态；最终可进入复盘 |
| 失败判定 | 死亡真人仍可提交游戏动作、看到未公开身份、旁观流程卡住 |
| 建议测试类型 | `e2e` |

### E2E-004：真人死亡后快进到复盘

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 真人玩家死亡并处于 `dead_spectating` |
| 操作步骤 | 点击 `快进到结局`；系统自动模拟剩余流程 |
| 期望结果 | 成功时进入 `review`；快进产生的规则事件完整写入日志；快进期间不允许真人插入普通游戏动作 |
| 失败判定 | 快进后缺失关键事件、直接伪造复盘、真人状态被恢复为可发言或可投票 |
| 建议测试类型 | `integration` + `e2e` |

### E2E-005：首轮 MVP 页面可被项目负责人跑通

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 开发阶段完成第一轮可运行骨架 |
| 操作步骤 | 项目负责人打开页面，从开局实际玩到复盘 |
| 期望结果 | 能跑通一局，且基础体验达标：知道下一步点哪里、聊天室消息能表达局势、复盘能说明本局发生了什么 |
| 失败判定 | 即使自动化测试通过，只要项目负责人认为“不像一个能玩下去的 AI 狼人杀 MVP”，不得进入下一开发阶段 |
| 建议测试类型 | `manual` |

## 规则引擎验收

### RULE-001：5 人最简局身份配置正确

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 创建标准 5 人局 |
| 操作步骤 | 生成玩家座位与身份 |
| 期望结果 | 仅包含 1 狼人、1 预言家、3 村民；真人占 1 个座位，其余为 AI |
| 失败判定 | 身份数量错误、出现 MVP 外身份、座位重复或缺失 |
| 建议测试类型 | `unit` |

### RULE-002：首夜禁止狼人刀真人

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 首夜，狼人提交击杀目标 |
| 操作步骤 | 检查合法目标列表并尝试选择真人玩家 |
| 期望结果 | 真人玩家不出现在合法目标中；强行提交真人目标返回错误且不写入 `TruthEvent` |
| 失败判定 | 首夜真人可被选为击杀目标，或非法尝试写入事件日志 |
| 建议测试类型 | `unit` |

### RULE-003：投票允许弃票但禁止自投

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 进入 `vote` 或 `tie_vote`，真人存活 |
| 操作步骤 | 提交弃票；再尝试提交自投 |
| 期望结果 | 弃票是合法选择；自投返回错误且不写入 `TruthEvent` |
| 失败判定 | 弃票被拒绝、自投被接受、自投尝试产生有效投票事件 |
| 建议测试类型 | `unit` |

### RULE-004：平票最多追加一次

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 首轮投票出现最高有效票平票 |
| 操作步骤 | 进入 `tie_speech`；完成拉票；进入 `tie_vote`；二次投票仍平票 |
| 期望结果 | 本轮无人放逐；进行胜负检查；未终局则进入下一夜 |
| 失败判定 | 无限循环平票流程、跳过二次投票、二次平票后未检查胜负 |
| 建议测试类型 | `unit` |

### RULE-005：死亡不默认公开身份

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 玩家因夜杀或放逐死亡 |
| 操作步骤 | 结算死亡并生成公开消息 |
| 期望结果 | 局中只公开死亡事实，不公开身份；终局复盘才公开所有身份 |
| 失败判定 | 天亮播报或放逐消息直接显示死者身份 |
| 建议测试类型 | `unit` + `integration` |

### RULE-006：胜负条件按简化人数规则触发

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 夜晚结算后、白天放逐后或平票无人放逐后 |
| 操作步骤 | 调用胜负检查 |
| 期望结果 | 狼人全部出局则好人胜；狼人数量大于等于好人数量则狼人胜 |
| 失败判定 | 胜负延迟、提前、使用未锁定的屠边或屠城规则 |
| 建议测试类型 | `unit` |

### RULE-007：非法动作不写入事实源

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 任意阶段收到非法 `GameAction` |
| 操作步骤 | 提交非法目标、重复提交、非当前阶段动作或权限不足动作 |
| 期望结果 | 返回标准错误；`TruthEvent` 数量与最后 `seq` 不变 |
| 失败判定 | 非法尝试被记录为业务事件，或改变 `GameSnapshot` |
| 建议测试类型 | `unit` + `integration` |

### RULE-008：有效状态改变动作必须携带 `idempotencyKey`

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 提交会改变对局状态的动作 |
| 操作步骤 | 分别提交缺失、重复和新的 `idempotencyKey` |
| 期望结果 | 缺失 key 的动作被拒绝；重复 key 不产生重复事件；新 key 的合法动作正常处理 |
| 失败判定 | 刷新或连点造成重复事件、同一投票或发言被写入多次 |
| 建议测试类型 | `unit` + `integration` |

## 状态机验收

### STATE-001：每个 `gamePhase` 只接受本阶段合法动作

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 遍历阶段2定义的全部 `gamePhase` |
| 操作步骤 | 对每个阶段提交合法动作与至少一个非法动作 |
| 期望结果 | 合法动作进入预期出口状态；非法动作返回错误且状态不变 |
| 失败判定 | 跨阶段动作被接受、状态跳转到未定义阶段 |
| 建议测试类型 | `unit` + `integration` |

### STATE-002：`dead_spectating` 覆盖普通操作权限

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 真人死亡，底层 `gamePhase` 仍在夜晚、发言、投票、拉票或遗言之一 |
| 操作步骤 | 尝试发言、投票、夜晚行动、拉票、遗言 |
| 期望结果 | 全部普通游戏动作被拒绝；只允许旁观或请求快进 |
| 失败判定 | 死亡真人仍可主动影响局势 |
| 建议测试类型 | `integration` |

### STATE-003：快进失败恢复为旁观

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 死亡真人请求快进，模拟过程中发生 AI 连续失败或状态推进异常 |
| 操作步骤 | 触发 `fast_forward_failed` |
| 期望结果 | 恢复到最近可旁观状态；`humanParticipationState` 恢复为 `dead_spectating`；显示失败消息 |
| 失败判定 | 快进失败后真人恢复为 `alive`、丢失原状态、无法继续旁观 |
| 建议测试类型 | `integration` |

### STATE-004：刷新恢复不允许重复提交

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 玩家已提交身份确认、夜晚行动、发言、投票或遗言之一 |
| 操作步骤 | 刷新页面并再次提交同一动作 |
| 期望结果 | 已提交动作不可重复写入；页面恢复到当前真实待办状态 |
| 失败判定 | 刷新后重复提交产生第二条业务事件 |
| 建议测试类型 | `integration` + `e2e` |

## 聊天室 UI 验收

### UI-001：每个阶段显示正确操作区和输入区状态

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 进入任一 `gamePhase` |
| 操作步骤 | 检查消息流、结构化操作区、输入框启用状态 |

### UI-002：按钮只提交映射表中的动作

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 页面展示任意结构化按钮 |
| 操作步骤 | 点击按钮并观察 Store 或规则入口收到的对象 |

### UI-003：自由文本限制与草稿保留

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 进入发言、拉票、遗言或复盘追问输入状态 |
| 操作步骤 | 提交空文本、超长文本、合法文本，并模拟提交失败 |
| 期望结果 | 空文本和超长文本显示系统错误；提交中禁用输入与按钮；成功后清空；失败后保留草稿 |
| 失败判定 | 空文本可提交、失败后文本丢失、提交中可重复点击 |
| 建议测试类型 | `e2e` |

### UI-004：错误与降级以系统消息展示

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 触发非法动作、重复提交、AI 降级、恢复失败之一 |
| 操作步骤 | 观察消息流和操作区 |
| 期望结果 | 以 `[系统]` 风格展示明确错误或降级提示；玩家知道下一步能做什么 |
| 失败判定 | 静默失败、页面只在控制台报错、玩家无法继续 |
| 建议测试类型 | `e2e` |

### UI-005：消息流不成为事实源

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 任意局中阶段 |
| 操作步骤 | 根据事件、快照和可见信息派生消息；尝试从 UI 消息反向修改规则事实 |
| 期望结果 | 消息流只显示派生内容；规则事实只来自规则引擎写入的 `TruthEvent` |
| 失败判定 | UI 消息文本被当成死亡、投票、身份或胜负事实来源 |
| 建议测试类型 | `integration` |

## AI 与降级验收

### AI-001：AI 局中任务只接收可见信息

| 字段 | 内容 |
| --- | --- |
| 前置条件 | AI 发言、夜晚行动、投票、拉票或遗言 |
| 操作步骤 | 捕获 AI Client 构造的请求上下文 |
| 期望结果 | 请求只包含该 AI 角色可见的 `VisibleInformationSnapshot`、公开发言、公开投票与合法目标 |
| 失败判定 | 请求中出现完整 `GameSnapshot`、未公开身份、未公开夜晚行动或其他角色私有信息 |
| 建议测试类型 | `integration` |

### AI-002：AI 失败先重试一次再降级

| 字段 | 内容 |
| --- | --- |
| 前置条件 | AI Proxy 超时、不可用或返回非法 JSON |
| 操作步骤 | 模拟第一次失败、第二次仍失败 |
| 期望结果 | 系统重试一次；仍失败后使用当前阶段安全降级策略；有效降级动作记录 `metadata.generatedBy = fallback` 与 `metadata.fallbackReason` |
| 失败判定 | 无重试、无限重试、失败后卡死、降级动作无来源记录 |
| 建议测试类型 | `integration` |

### AI-003：AI 输出不能改变规则事实

| 字段 | 内容 |
| --- | --- |
| 前置条件 | AI 返回发言、投票理由、行动依据或复盘解释 |
| 操作步骤 | 检查规则事实变更来源 |
| 期望结果 | 身份、死亡、投票、胜负只由规则引擎根据合法动作结算 |
| 失败判定 | AI 文本直接决定死亡、身份公开、胜负或事件写入 |
| 建议测试类型 | `integration` |

### AI-004：前端不得读取 API key

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 构建前端与启动 AI Proxy |
| 操作步骤 | 检查前端环境变量、打包产物和请求路径 |
| 期望结果 | API key 只存在服务端代理环境变量；前端只访问统一 AI Proxy 接口 |
| 失败判定 | 前端代码、浏览器环境或打包产物可读取 OpenAI API key |
| 建议测试类型 | `integration` |

## 存储与恢复验收

### STORE-001：`TruthEvent` 是唯一事实源

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 存在一局包含多阶段事件的对局 |
| 操作步骤 | 从 `TruthEvent` 重放生成快照；与当前快照比较 |
| 期望结果 | 重放结果与当前有效快照一致；冲突时以 `TruthEvent` 为准 |
| 失败判定 | Store、UI 消息或缓存字段覆盖事件事实 |
| 建议测试类型 | `integration` |

### STORE-002：快照损坏优先事件重放

| 字段 | 内容 |
| --- | --- |
| 前置条件 | IndexedDB 中存在事件日志和损坏或过期的 `GameSnapshot` |
| 操作步骤 | 启动 App 并执行恢复流程 |
| 期望结果 | 检测 `schemaVersion` 或 `lastEventSeq` 异常后从事件重放；恢复后重新生成当前可见信息 |
| 失败判定 | 直接使用损坏快照、恢复到错误阶段、可见信息未刷新 |
| 建议测试类型 | `integration` |

### STORE-003：事件重放失败给出清空当前局入口

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 事件日志缺失关键事件或无法重放 |
| 操作步骤 | 启动 App 恢复当前局 |
| 期望结果 | 显示恢复失败提示，并提供清空当前局重新开始的明确入口 |
| 失败判定 | 白屏、无限加载、静默丢弃旧局、自动伪造缺失事件 |
| 建议测试类型 | `integration` + `e2e` |

### STORE-004：新开局覆盖 MVP 当前局

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 已有当前局，用户选择新开一局 |
| 操作步骤 | 确认新开后创建新 `currentGame` |
| 期望结果 | MVP 只保留当前局入口；旧局不污染新局状态 |
| 失败判定 | 新旧事件混合、旧快照影响新局、未确认就覆盖当前局 |
| 建议测试类型 | `integration` |

## 信息隔离红线验收

### ISO-001：局中 UI 只渲染 `VisibleInformationSnapshot`

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 任意非 `review` 阶段 |
| 操作步骤 | 检查 UI 获取和渲染的信息来源 |
| 期望结果 | UI 只使用过滤后的可见信息、`PendingAction`、Store 状态和 `AppError` 派生消息 |
| 失败判定 | UI 直接读取完整身份、完整夜晚行动、完整 `GameSnapshot` 或未公开事件 |
| 建议测试类型 | `integration` + `e2e` |

### ISO-002：非 `review` 阶段禁止构造或发送 `ReviewContext`

| 字段 | 内容 |
| --- | --- |
| 前置条件 | `gamePhase` 不是 `review` |
| 操作步骤 | 尝试触发复盘追问或构造 `ReviewContext` |
| 期望结果 | 请求被阻止；前端不显示复盘追问入口；AI Client 不发送 `ReviewContext` |
| 失败判定 | 局中任意阶段可访问完整真相上下文 |
| 建议测试类型 | `integration` |

### ISO-003：预言家查验结果仅对本人可见

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 预言家完成查验且未到终局 |
| 操作步骤 | 分别为预言家、狼人、村民和真人不同身份生成可见信息 |
| 期望结果 | 只有预言家本人可见查验结果；终局复盘公开 |
| 失败判定 | 其他局中角色看到查验结果，或公开消息泄露查验结果 |
| 建议测试类型 | `unit` |

### ISO-004：死亡身份局中不公开

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 玩家夜死或被放逐 |
| 操作步骤 | 生成局中可见信息与聊天室消息 |

| 失败判定 | 非复盘阶段的消息或 AI 输入包含死者身份 |
| 建议测试类型 | `unit` + `integration` |

## 复盘验收

### REVIEW-001：进入复盘后公开完整真相

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 胜负已触发，进入 `review` |
| 操作步骤 | 打开复盘总览 |
| 期望结果 | 展示所有玩家身份、夜晚行动、所有发言原文、投票票型、平票记录和胜负原因；摘要只能作为发言原文之外的附加说明，不得替代原文 |
| 失败判定 | 缺失关键事实、与 `TruthEvent` 冲突、仍按局中可见性隐藏终局真相 |
| 建议测试类型 | `integration` + `e2e` |

### REVIEW-002：复盘追问只能基于本局记录回答

| 字段 | 内容 |
| --- | --- |
| 前置条件 | `gamePhase = review`，玩家提交追问 |
| 操作步骤 | 询问本局发生原因、某名玩家行为、胜负关键点，以及超出本局记录的问题 |
| 期望结果 | AI 回答基于本局真实记录；能区分局中当时可见信息与终局揭示真相；超出记录范围时说明无法确定 |
| 失败判定 | 编造未发生事件、把无记录心理活动当事实、混淆局中视角与终局真相 |
| 建议测试类型 | `integration` + `e2e` |

### REVIEW-003：开始新局前清理或覆盖当前局

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 处于 `review` |
| 操作步骤 | 点击 `开始新局` |
| 期望结果 | 返回 `mode_select` 或创建新局前明确处理当前局；新局不继承旧局事件和快照 |
| 失败判定 | 旧局状态残留、复盘追问上下文污染新局 |
| 建议测试类型 | `integration` + `e2e` |

## 人类 MVP 体验验收

### HITL-001：项目负责人跑通 MVP 并确认基础体验

| 字段 | 内容 |
| --- | --- |
| 前置条件 | 第一轮可运行骨架已通过 AI 自动化测试与 Reviewer Agent 审查 |
| 操作步骤 | 项目负责人打开本地页面，亲自从开局玩到复盘 |
| 通过条件 | 能顺利开始一局；能完成夜晚、天亮、发言、投票、死亡旁观或继续游戏、终局复盘；页面没有明显卡死、迷路、按钮不知道点哪个的问题；聊天室体验基本像一局 AI 狼人杀；复盘能帮助理解本局 |
| 失败判定 | 跑不完一局；玩家不知道下一步；聊天室像普通问答而不是游戏；死亡后体验混乱；复盘没有解释价值 |
| 建议测试类型 | `manual` |

HITL 结论优先级高于自动化测试通过状态。若 `HITL-001` 未通过，项目不得进入后续功能扩展，只能回到当前开发阶段修正 MVP 骨架体验。

## AI 自动验收最低覆盖要求

进入阶段9开发后，每个开发切片至少满足：

1. 涉及规则结算的切片，必须覆盖对应 `RULE` 用例。
2. 涉及阶段推进的切片，必须覆盖对应 `STATE` 用例。
3. 涉及 UI 的切片，必须覆盖对应 `UI` 或 `E2E` 用例。
4. 涉及 AI 调用的切片，必须覆盖 `AI` 与 `ISO` 用例。
5. 涉及存储恢复的切片，必须覆盖 `STORE` 用例。
6. 任何切片不得破坏 `ISO-001` 与 `ISO-002`，这两项为红线验收。

Reviewer Agent 审查时必须给出：

- 已覆盖的用例编号。
- 未覆盖用例及原因。
- 自动化测试命令或可重复验证方式。
- 若驳回，必须说明违反的阶段文档条款和建议修正方向。
