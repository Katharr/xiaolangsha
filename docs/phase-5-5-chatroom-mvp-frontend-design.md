## 回溯清单

本阶段不推翻阶段1至阶段5的核心业务、数据和接口设计，只收缩 UI 表现层复杂度。

回溯项：

1. 放弃“卡牌战斗风为主、桌游主持人风为结构骨架”的第一版前端方向。
2. 放弃第一版 AI 美术素材生成工作流和素材需求清单。
3. 删除或忽略 `docs/art-asset-generation-brief.md` 相关路线；MVP 不需要任何美术素材。

影响范围：

- 阶段6测试与验收设计应优先验证游戏闭环、规则动作和信息隔离，而不是视觉效果。
- 阶段7生成项目规则时，应明确第一版前端目标是“能玩、能恢复、能复盘”，不是“好看”。

## 锁定设计

1. MVP 前端采用接近 CLI 的 Web 聊天室形式。
2. 主界面由“状态栏 + 消息流 + 结构化操作区 + 输入区”组成。
3. 所有规则动作必须通过结构化按钮、选择器或确认控件提交，不靠自然语言解析。
4. 玩家自由输入只用于白天发言、平票拉票、放逐遗言和复盘追问。
5. 局中 UI 只能渲染 `VisibleInformationSnapshot` 允许的信息，不读取完整 `TruthEvent` 或完整 `GameSnapshot`。
6. 非 `review` 阶段不得构造或发送 `ReviewContext`。
7. 第一版不做美术、不做动画、不做复杂响应式布局；只保证桌面浏览器可用，移动端可作为后续增强。

## 体验目标

第一版目标是尽快让项目“成型”：玩家能从网页打开游戏，开始一局 5 人狼人杀，看到主持人播报和 AI 发言，用按钮完成夜晚行动与投票，最终进入复盘。

体验关键词：

- 低成本：不用美术素材，不做复杂 UI。
- 可玩：完整跑通一局。
- 可测：每个动作和消息都能映射到状态机与事件日志。
- 可维护：后续可在聊天流基础上再升级视觉表现。

## 页面布局

```text
┌──────────────────────────────────────────────┐
│ 顶部状态栏：阶段 / 轮次 / 你的身份 / 存活玩家 │
├──────────────────────────────────────────────┤
│ 消息流                                       │
│ [系统] 游戏开始                              │
│ [主持人] 昨夜 3 号死亡                       │
│ [2号 AI] 我觉得 4 号很可疑                   │
│ [你] 我先听后置位发言                        │
│ [系统] 请投票                                │
├──────────────────────────────────────────────┤
│ 结构化操作区：目标选择 / 投票 / 弃票 / 确认   │
├──────────────────────────────────────────────┤
│ 输入区：文本框 + 发送按钮                    │
└──────────────────────────────────────────────┘
```

布局规则：

1. 顶部状态栏始终显示当前 `gamePhase`、轮次、真人身份摘要、存活/死亡玩家。
2. 消息流是主区域，按发生顺序追加消息。
3. 结构化操作区只显示当前允许的动作。
4. 输入区只在允许自由输入时启用，否则禁用并显示当前需要等待或选择的操作。
5. 页面外壳在桌面端固定在一个视口内，顶部状态栏、结构化操作区和输入区保持可见；只有消息流内部滚动，避免长消息把操作区挤出屏幕。

## 消息类型

| 消息类型 | 来源 | 内容 | 局中可见性 |
| --- | --- | --- | --- |
| `system` | 系统 | 创建对局、恢复成功、错误提示、降级提示 | 按 UI 当前视角展示 |
| `host` | 规则/主持人 | 阶段切换、天亮播报、投票开始、胜负播报 | 公开 |
| `human_speech` | 真人 | 白天发言、拉票、遗言 | 公开或按阶段展示 |
| `ai_speech` | AI | AI 发言、拉票、遗言 | 公开 |
| `private_info` | 规则引擎 | 你的身份、查验结果、你的夜晚行动结果 | 仅真人可见 |
| `action_prompt` | Store/UI | 当前需要你做什么 | 仅真人 UI |
| `vote_result` | 规则引擎 | 投票票型、放逐结果、无人放逐 | 公开 |
| `review_truth` | 复盘 | 真实身份、夜晚行动、投票、胜负原因 | 仅 `review` 阶段 |
| `review_answer` | AI 复盘 | 对玩家追问的回答 | 仅 `review` 阶段 |

消息生成原则：

- 不是每个 `TruthEvent` 都必须显示成一条消息，但每个玩家需要理解的阶段推进必须有消息。
- 私有信息必须有明显前缀，例如 `[仅你可见]`。
- AI 降级时可显示简短系统消息，例如 `[系统] AI 响应失败，已使用安全降级继续流程。`

## 可见信息到消息的映射

聊天室消息是 UI 派生视图，不是事实源。UI 不得直接读取完整 `TruthEvent` 或完整 `GameSnapshot` 来生成局中消息，只能基于 `VisibleInformationSnapshot`、当前 `PendingAction`、Store 状态和统一错误对象生成。

建议的前端消息模型：

| 字段 | 说明 |
| --- | --- |
| `messageId` | UI 消息 ID，可由 `eventId`、`seq` 或本地错误 ID 派生 |
| `kind` | 对应上方消息类型 |
| `text` | 最终展示文本 |
| `sourceEventId?` | 若来自可见事件，保存来源 `eventId` |
| `seq?` | 若来自可见事件，保存来源 `seq` |
| `visibility` | `public`、`private`、`review_only`、`ui_only` |

映射规则：

| 输入来源 | 生成消息 | 事件追踪 | 约束 |
| --- | --- | --- | --- |
| `VisibleInformationSnapshot.publicEvents` | `host`、`vote_result` 或公开阶段消息 | 必须保留 `eventId` / `seq` | 只展示 payload 中已过滤后的公开内容 |
| `VisibleInformationSnapshot.privateEvents` | `private_info` | 必须保留 `eventId` / `seq` | 必须带 `[仅你可见]` 前缀，不进入公开消息流语义 |
| `VisibleInformationSnapshot.speeches` | `human_speech` 或 `ai_speech` | 必须保留对应发言 `eventId` | 只展示发言原文 `text`，不得用摘要替代 |
| `VisibleInformationSnapshot.votes` | `vote_result` 或票型消息 | 必须保留对应投票事件 `eventId` | 投票提交中不展示未结算票型 |
| `VisibleInformationSnapshot.legalActions` / `nextPendingAction` | `action_prompt` 和操作区按钮 | 无事件 ID | 只产生可执行提示，不写事实 |
| `humanParticipationState` | 旁观、快进、只读提示 | 无事件 ID | 死亡旁观不获得隐藏身份或隐藏行动 |
| `AppError.userMessage` | `system` 错误消息 | 可带 `error.code` | 不显示原始异常堆栈或服务端密钥信息 |
| `ReviewContext` | `review_truth`、`review_answer` | 可引用事件 ID | 仅 `review` 阶段允许构造和发送 |

## 结构化操作区

标准局与练习/自由局入口必须区分：标准局从 `mode_select` 直接创建随机身份对局，并进入随机身份后的 `role_reveal`；`role_setup` 仅用于练习/自由局的手动身份选择。

| `gamePhase` | 操作区内容 | 输入区状态 |
| --- | --- | --- |
| `mode_select` | `开始标准局`、`练习/自由局`、若有旧局则 `继续对局` / `新开一局` | 禁用 |
| `role_setup` | 身份选择：狼人、预言家、村民；`确认身份` | 禁用 |
| `role_reveal` | `确认进入首夜` | 禁用 |
| `night_action` | 若有夜晚行动：目标下拉/按钮 + `提交夜晚行动`；若无行动：`继续等待` | 禁用 |
| `day_announcement` | `进入发言` | 禁用 |
| `day_speech` | 非真人轮次无操作；真人轮次显示 `发送发言` | 真人轮次启用 |
| `vote` | 存活目标按钮、`弃票`、`提交投票` | 禁用 |
| `tie_speech` | 真人是平票玩家时启用 `发送拉票发言`，否则等待 | 按权限启用 |
| `tie_vote` | 存活目标按钮、`弃票`、`提交二次投票` | 禁用 |
| `exile_last_words` | 真人被放逐时启用 `提交遗言`，否则等待 | 按权限启用 |
| `fast_forwarding` | 显示自动推进中；失败后显示 `继续旁观` / `再次尝试快进` | 禁用 |
| `review` | `开始新局`、复盘追问输入 | 追问输入启用 |

约束：

- 自投按钮不显示或显示为禁用。
- 非法目标不进入可选列表。
- 所有改变状态的按钮提交时必须携带 `idempotencyKey`。
- 提交中按钮禁用，防止重复点击。

### `humanParticipationState` 跨阶段 UI 规则

`humanParticipationState` 覆盖在 `gamePhase` 之上，用来决定真人是否还能主动参与。

| 状态 | UI 规则 |
| --- | --- |
| `alive` | 按当前 `gamePhase` 正常展示操作区和输入区 |
| `dead_spectating` | 除 `review` 外默认只读；消息流继续展示公开信息；操作区提供 `快进到结局` 和 `继续旁观` |
| `fast_forwarded` | 进入 `fast_forwarding`；隐藏普通发言、投票和夜晚行动入口，只显示自动推进状态 |

快进失败时，UI 必须恢复为 `dead_spectating` 的只读旁观状态，并显示失败消息；不得把真人恢复为可发言或可投票状态。

### 按钮到 `GameAction` 的映射

| UI 操作 | 提交对象 | 说明 |
| --- | --- | --- |
| `开始标准局` | `create_game`，`mode = standard` | 标准局随机身份，成功后进入 `role_reveal` |
| `练习/自由局` | `create_game`，`mode = free` | 成功后进入 `role_setup` |
| `确认身份` | `confirm_role_setup` | 仅 `role_setup` 使用，必须包含 `selectedRole` |
| `确认进入首夜` | `confirm_role_reveal` | 身份揭示后进入首夜 |
| `提交夜晚行动` | `submit_night_action` | 目标必须来自合法目标列表 |
| `进入发言` | `confirm_day_announcement` | 天亮播报确认后进入发言 |
| `发送发言` | `submit_speech` | 仅真人发言轮次启用 |
| `提交投票` | `submit_vote`，`voteRound = first` | `choiceType` 为 `target` 或 `abstain` |
| `发送拉票发言` | `submit_tie_speech` | 仅真人是平票玩家时启用 |
| `提交二次投票` | `submit_vote`，`voteRound = tie_break` | 仍允许弃票，不允许自投 |
| `提交遗言` | `submit_last_words` | 仅真人被放逐且需要遗言时启用 |
| `快进到结局` | `request_fast_forward` | 仅死亡旁观者可用 |
| `开始新局` | `confirm_new_game` | 复盘后清理或覆盖当前局 |
| `提交复盘追问` | `requestAiResponse(taskType = review_question)` | 不是 `GameAction`；仅 `review` 阶段允许，并必须使用 `ReviewContext` |

### 自由文本输入限制

| 场景 | 最小长度 | 最大长度 | 失败提示 |
| --- | --- | --- | --- |
| 白天发言 | 去空格后 1 字符 | 500 字符 | `[系统] 发言不能为空，且不能超过 500 字。` |
| 平票拉票 | 去空格后 1 字符 | 500 字符 | `[系统] 拉票发言不能为空，且不能超过 500 字。` |
| 放逐遗言 | 去空格后 1 字符 | 500 字符 | `[系统] 遗言不能为空，且不能超过 500 字。` |
| 复盘追问 | 去空格后 1 字符 | 300 字符 | `[系统] 追问不能为空，且不能超过 300 字。` |

文本规则：

- 提交中禁用输入框和发送按钮。
- 提交成功后清空输入框。
- 提交失败时保留草稿，方便玩家修改后重试。
- 所有用户输入按纯文本渲染，不允许作为 HTML 注入页面。

## 信息展示

顶部状态栏最少显示：

- 当前阶段，例如 `白天发言`、`投票`、`复盘`
- 当前轮次，例如 `第1天`、`第2夜`
- 你的身份，例如 `你是：预言家`
- 玩家列表简表，例如 `1号 你 存活 / 2号 AI 存活 / 3号 AI 死亡`

局中禁止：

- 显示 AI 真实身份。
- 显示完整真相日志。
- 显示未公开夜晚目标。
- 在非 `review` 阶段展示 `ReviewContext` 派生内容。

复盘阶段允许：

- 展示所有真实身份。
- 展示夜晚行动、投票、发言和胜负原因。
- 允许玩家用输入框向 AI 追问，但回答必须基于真实记录。

复盘阶段最小展示内容：

1. 每名玩家的座位、控制者、真实身份、阵营和最终存活状态。
2. 每晚夜晚行动与结果。
3. 每天投票、平票、二次投票和放逐结果。
4. 所有发言原文，包括白天发言、拉票和遗言。
5. 最终胜负方与 `winReason`。
6. 复盘追问输入区。

只有 `review` 阶段允许 Store 组装 `ReviewContext` 并调用 `review_question`；局中任何阶段都不得为了聊天展示提前构造完整真相上下文。

## 错误与恢复

错误展示采用普通消息流，不做复杂弹窗：

| `AppError.code` | 展示消息 | 是否可重试 |
| --- | --- | --- |
| `INVALID_ACTION` | `[系统] 当前操作不合法。` | 否 |
| `ACTION_NOT_ALLOWED` | `[系统] 当前阶段不能执行该操作。` | 否 |
| `DUPLICATE_SUBMIT` | `[系统] 该操作已提交，请勿重复点击。` | 否 |
| `STORAGE_LOAD_FAILED` | `[系统] 读取当前对局失败。` | 是，允许重新加载或清空当前局 |
| `STORAGE_SAVE_FAILED` | `[系统] 保存失败，请重试。` | 是 |
| `AI_TIMEOUT` | `[系统] AI 响应超时，正在使用安全降级。` | 否，局中流程继续 |
| `AI_JSON_INVALID` | `[系统] AI 返回格式不可用，正在使用安全降级。` | 否，局中流程继续 |
| `AI_UNAVAILABLE` | `[系统] AI 暂时不可用，已使用安全降级。` | 否，局中流程继续 |
| `SNAPSHOT_CORRUPTED` | `[系统] 快照损坏，正在尝试从事件记录恢复。` | 是 |
| `REPLAY_FAILED` | `[系统] 事件重放失败，请清空当前局并重新开始。` | 否，只允许清空当前局 |

若 `AppError.userMessage` 存在，优先展示 `userMessage`；否则使用上表兜底文案。UI 不展示原始异常堆栈。

快进失败必须显示失败原因摘要，并在操作区提供 `继续旁观`；只有当规则层允许再次尝试时才显示 `再次尝试快进`。

## MVP 骨架交付范围

第一轮可运行骨架必须实现：

1. 单页面聊天室布局。
2. 顶部状态栏。
3. 消息流。
4. 结构化操作区。
5. 文本输入区。
6. `mode_select`、`role_setup`、`role_reveal`、`night_action`、`day_announcement`、`day_speech`、`vote`、`tie_speech`、`tie_vote`、`exile_last_words`、`fast_forwarding`、`review` 的最小展示和动作入口。
7. 刷新恢复后的当前状态展示。
8. 复盘追问入口。

明确不做：

- 美术素材。
- 头像、背景图、动画。
- 移动端专项适配。
- 复杂主题切换。
- 自然语言驱动规则动作。

## 阶段6输入项

阶段6测试与验收设计必须覆盖：

1. 每个 `gamePhase` 是否显示正确消息、操作区和输入区状态。
2. 结构化按钮是否只提交合法 `GameAction`，且按钮到 `GameAction` 的映射正确。
3. 非法动作、重复提交、AI 降级、恢复失败是否以系统消息展示。
4. 局中 UI 是否只渲染 `VisibleInformationSnapshot`。
5. 非 `review` 阶段是否禁止构造或发送 `ReviewContext`。
6. 复盘追问是否只在 `review` 阶段启用。
7. 一局 MVP 是否可从开始跑到复盘。
8. `dead_spectating` 是否跨阶段保持只读，并提供快进/继续旁观。
9. 自由文本输入是否覆盖空文本、超长、提交中禁用、失败保留草稿。

## 阶段5与阶段5.5门禁审查

审查结论：阶段5系统与接口设计、阶段5.5极简聊天室式前端设计均满足当前项目需求，可以进入阶段6“测试与验收设计”。

审查依据：

1. 阶段5已定义 `ui / store / rules / storage / ai-client / ai-proxy / shared` 模块边界，聊天室前端只收缩 `ui` 表现层，不改变模块依赖。
2. 阶段5的 `GameAction` 已覆盖聊天室操作区所需动作：创建对局、自由局选身份、确认身份、夜晚行动、天亮确认、发言、投票、拉票、遗言、快进和新局。
3. 阶段5的 AI Client/Proxy 仍适用：局中 AI 任务使用 `VisibleInformationSnapshot`，复盘追问使用 `ReviewContext`，且非 `review` 阶段禁止构造或发送 `ReviewContext`。
4. 阶段5.5明确消息流是 UI 派生视图，不是事实源；局中消息只能由过滤后的可见信息、`PendingAction`、Store 状态和 `AppError` 派生。
5. 阶段5.5保留结构化按钮完成规则动作，避免退化为普通聊天机器人，符合阶段1核心反用例。
6. 阶段5.5覆盖阶段2的双层状态模型，尤其是 `dead_spectating` 只读旁观、快进入口和快进失败恢复。
